# ReClaude CLI 初始化失败的安全边界

修复只涉及原生 Relay 适配层，不改变 Claude CLI、授权、出口守卫、账号并发、计费协议或 Pro 槽。

## 顺序

原流程在原生 CLI 初始化前把调用写成 `in_flight`。初始化没有派发模型请求时，异常仍将已完成历史的续接点覆盖为 `failed`，后续客户调用因 no-replay 被永久拒绝。

新流程先验证调用方历史和配置，再准备 CLI。只有初始化成功后才登记本次请求的 `seen`、新历史和 `in_flight`，然后发出一次模型授权和用户输入。历史工具结果也遵守同一顺序。不存在内部重试或非流式回退。

## 失败处理

仅 `native_initialize_not_ready_no_dispatch` 可使用原准备边界，且必须同时满足：

- 原续接点通过已有配置、历史和原生消息标识验证；全新会话不得带旧模型授权或消费记录。
- 原生 CLI 和派发代理均已停止，stdout 读取线程已退出。
- 当前代理关闭过程中获得的新鲜计数为零上游尝试、零拒绝；旧磁盘健康快照不构成证明。
- 当前代理的会话与地址匹配；checkpoint、tools、grant 和所有 consumed 文件字节与准备前相同，不存在残留临时授权。

通过后保留原 checkpoint、已消费记录、seen 和工具等待边界，回收当前 CLI。本次请求仍返回明确错误；只有下一次真实客户请求可重新准备。验证缺失、状态变化、非零派发、未知终态仍按原 no-replay 保护处理。

已有 `failed` / `in_flight` 不自动迁移。原安全 checkpoint 已被覆盖时，不能仅凭零派发错误、目录时间或消费次数恢复；旧付费请求不得重放。应另行保全证据并审查安全恢复方案。

## 诊断

HTTP 审计增加由既有 tenant 与调用方 canonical session UUID 生成的 `session_pool_key` 摘要，便于与会话目录直接关联。可选 `gateway_request_id` 只接受标准 UUID。不得记录原始 metadata、授权、API key 或提示词。

## 回归与上线

隔离测试覆盖初始化失败后的下一次调用、已有付费历史、工具续接、配置变化、消费记录变化、未知计数、旧 failed 拒绝及租户隔离。真实生产接口不得用旧请求验收。候选应先独立代码审阅；仅更新获准的独立 Relay worker，核验原出口和账号隔离，保留原始失败证据，不重启主网关。
