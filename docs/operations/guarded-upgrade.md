# 带固定出口的升级与恢复

适用于保留已有槽位、账号和代理的升级。复用原生管理 API；不要直接改 VM JSON/DB，不把出口 `rearm` 写进自动重试或巡检。

## 升级成功必须证明什么

容器 Running 和 kernel HTTP 200 都不足以证明槽位可入池。原生 `/reload` 可以启动容器却保留逻辑 `status: stopped`；`/schedulable` 只改调度开关。结果是入池失败503，下游重试后可能显示502。

`scripts/panel-upgrade.sh` 现记录更新前健康槽位的调度意图、proxy ID、有效并发及已批准IP；更新后同时核对：

- 逻辑状态 `running`、原有调度开关、相同代理与并发；
- 内核鉴权/进程健康，允许内核忙碌但健康；
- strict要求没有被关闭，获批IP没有改变；守卫ready、未锁存、观测与批准IP相同、策略revision一致且检测不超过120秒；
- helper更新后再次检查，全部通过才更新宿主VERSION并报告成功。

任何失败都不能当成发布完成。检查器仅GET，不会自动启动槽或修改IP、策略revision、凭据和锁存。升级前已停止的槽不被纳入恢复名单；手动停调度状态保持。

## 自定义 Compose / 定向发布

自定义生产部署应保留自己的镜像、端口、挂载和资源配置。下面两个模式只做原生只读核验，可作为任何定向发布流程的前后步骤；不要为了运行核验而执行该脚本的完整升级模式。

1. **在暂停调度或重启之前**保存快照。使用受限、唯一的发布目录；核对快照ID与本次批准更新的槽位完全一致，不接受意外空数组。

   ```sh
   umask 077
   sh scripts/panel-upgrade.sh --snapshot-slots vm2api > slots-before.json
   python3 -c 'import json,sys; rows=json.load(open(sys.argv[1])); assert {x["id"] for x in rows} == set(sys.argv[2:])' slots-before.json slot-a
   ```

   `slot-a`和容器名应替换为本次已批准的目标，不存管理员key。脚本从容器原有环境取得认证。快照不含凭据。保持原快照，不能在故障发生后重新抓取并冒充升级前基线。

2. 用原生调度hold排空；保留当前DB/策略/配置/凭据备份；只更新本次批准的槽。生产 `KIN_AUTO_SYNC_WRAP=0`，原生 `wrap-cli/sync` 必须显式指定IDs。
3. 检查固定出口。若锁存、IP不符、探测失败或状态过期，保持停机并报告阻塞。**IP不同不能直接接受新值；本步骤没有自动rearm。**
4. 如原在用槽位已被守卫停掉，先由管理员调查原因。只有在仍为同一批准IP、且管理员明确授权后，才单独使用原生 `POST /api/panel/proxy-exit-guard/:proxyId/rearm`（提交相同expected_ip），随后重新读取守卫验证结果。它不会替代槽位启动。
5. 对**升级前快照中的目标槽**，确认原代理仍绑定、没有其他可分配的获批备用代理、账号凭据合法可用、并发没有改变后，用原生 **`POST /api/panel/vms/:id/start`**，不要只 `/reload` 或打开调度。原生start可能分配代理，因此不能省略绑定检查或批量启动其他停止的槽。
6. 运行同一个只读门禁；非零退出就停止发布验收：

   ```sh
   sh scripts/panel-upgrade.sh --verify-slots vm2api slots-before.json
   ```

7. 两端检查key范围、独占组和实际请求归属；必要时进行最小JSON/SSE验收，核对结束事件，不用一条HTTP200代替完整验收。保存失败及跳过证据。

## 流式验收的证据

只在空闲且固定出口守卫通过时发起新的合成测试。每个意图先保存唯一ID、请求和预期结果，禁止自动重发；结果不明先只读查两端日志和账本。只保存本次合成请求的原始SSE（受限目录和0600权限），保持正常业务内容日志关闭，不为排障收集其他用户的正文。不要只保存一个成功/失败布尔值，否则无法回溯精确回显失败。

使用原生消息组装器离线核对已保存响应，不再只拼接 `text_delta`：`content_block_start` 中的初始文本也属于响应。下面的工具不访问网络，不发送或重放请求，标准输出仅含摘要、哈希、事件和计量，不含响应正文。

```sh
node scripts/sse-acceptance.mjs /private/own-synthetic-response.sse EXPECTED_MARKER
```

必须分别核对 HTTP 状态、`stream_complete`、`exact_text`、实际槽位/session归属和两端用量。截断、error事件、错误事件顺序或内容不匹配都不能计为全通过；`legacy_exact_text` 仅用于判断旧增量拼接器是否漏掉初始文本。旧响应没有保存时，不根据一次新测试通过倒推旧失败的确定原因。

会话隔离验收可使用同一受限key下两个独立session和随机标记，串行执行A首轮、B无历史查询、A携带自身历史续接；确认B看不到A标记、A的出站session不变、B的session不同。只核获准账号，封禁槽位保持停用。前缀缓存命中不等于加载其他会话历史。

逐次读取 `request_attempts`，不能把一个客户端POST误记成一个上游attempt。若原生调度发生重试，保留每次状态、是否已向下游提交和usage；无usage只表示未取得计量，不能证明供应商没有消耗额度。验收客户端不能再重放已完成或结果不明的请求。

## 限制与回退

这是升级状态验收和显式恢复流程，不是永久VM→代理锁定或账号可用性保证。原生start的绑定能力仍受代理池容量约束；扩池或解绑旧槽前应重新审查。

**主网关重启也属于出口维护。** Mihomo、kin-egress 与网关同容器时，重启会同时终止这些进程；原生守卫可产生 `exit_guard_restart_requires_rearm`，即使重启前后 IP 相同。排空请求不等于能够自动恢复。准备发布前必须核对实际进程归属和该版本的重启行为；完成补丁、回归及恢复方案后，在执行重启前取得本次同 IP 恢复授权。没有授权时仅应用可热加载的原生配置，保留代码补丁等待维护，不先重启再申请解锁。恢复只能使用已经批准的 IP，双源检测相符后通过原生 rearm/start 核验；不删除状态文件，也不改写预期 IP。

只读模式可在现网安装，不需要重启控制面。运行中的控制面可能仍缓存旧版面板升级脚本；下次正常更新镜像后，新面板脚本才随程序生效。在此之前，自定义发布必须使用宿主上的本版只读模式。`deploy/install.sh`不是本自定义部署的完整发布事务，不能用它的成功提示替代这里的基线验收。

镜像回退前也先保存当前状态；旧账号池或退休账号快照不能覆盖当前DB/HOME。不要删除出口状态文件消除锁存。

## 探测失败的诊断与 helper 定向更新

`exit_ip_probe_failed` 表示没有完成可信的出口验证，不能据此判定 IP 已变更。先保存 `data/run/egress/<proxyId>/exit-guard-state.json`，查看 `probe.stage`、`error_kind`、`duration_ms` 和 `http_status`；它们不包含代理凭据、查询 URL 或响应原文。同策略重启和退出清理保留首次锁存原因、观测 IP、检测时间及探测详情。旧版没有这些字段，不能事后还原其具体网络错误。

新 helper 的一次验证总预算为 10 秒，默认监控间隔仍为 15 秒。瞬时网络错误和检测端 429/500/502/503/504 最多尝试 3 次，间隔 250ms；checking 期间暂停新连接，暂时保留已有流。IP 不符、证书/响应不可信立即锁存；持续探测失败仍锁存并关闭连接。单个请求取消不再作为代理故障。没有自动解除已有锁存、备用探测源放行或自动接受新 IP，供应商持续断网仍需排障。

仅替换 helper 时，要同时检查 `/proc/<pid>/exe` 和原生面板守卫状态。直接覆盖正在执行的二进制可能使旧进程呈现 `kin-egress (deleted)`，从而被健康检查停用。Linux 上可先在隔离进程验证 `renameat2(RENAME_EXCHANGE)`：候选与旧文件放在同一已挂载目录树的不同子目录，两个文件名均保留 `kin-egress`，原子交换后旧进程对应文件仍存在且名称有效。**旧进程退出前不能删除它对应的文件。** 不支持安全交换时，应安排受控维护，不以忽略进程归属检查代替。

交换文件本身不解锁、不重启任何账号。只对明确获批的槽执行上方同 IP `rearm` 和原生 `/start`；逐一核对该槽实际执行的新二进制摘要、其他槽的 PID/策略/容器启动时间、两槽固定出口和完整流式结束事件。未重启的 helper 仍运行原版本，应在交接中明确标注，不能把磁盘文件摘要当成所有运行进程的版本。

## 下游调度与维护恢复

维护开始前同步在下游原生停调度，并保留账号组、亲和标签、独立 key 和并发。vm2api 的前置 `503/pool_unavailable` 不代表真实模型调用：核对 `request_attempts` 和 `attempt_count`，不要按请求日志行数估算模型消耗。

Sub2API 可为这个上游账号配置原生临时不可调度规则：HTTP503、关键词 `pool_unavailable`、`scope=account`、1分钟。只作用于该账号，不把普通429、模型限流或请求参数错误泛化成整池故障。短冷却限制持续锁停时的探测频率；它到期不解除 vm2api 的出口锁存。使用包含原生错误策略排除传递修复的版本，避免503选号耗尽又清掉排除集反复选择同一个已停池。

上线验收先验证槽实际 running、同IP守卫ready，再用原独立key完成最小JSON/SSE请求、核对单槽唯一attempt和usage；通过后才恢复下游原生调度。维护前已封禁/撤权/锁存的账号不在恢复名单，不能根据旧健康快照恢复。
