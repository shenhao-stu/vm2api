Integration baseline: fork `d5464c9ed87060867ccdfb7f413437dbd11ba36b`.

The merge retains the official implementation for protocol updates, quota reset handling, official terminal login, service updates and optional cluster direct links. The official source-map dependency fix (#599) is already equivalent to the fork fix and remains one override. The payload manifest is authoritative: upgrading from this fork's earlier baseline also requires the pinned kernel/CLI payload, even though the v1.3.201 release alone says a payload update is unnecessary from its immediate predecessor.

## Preserved behavior

- Native exit-IP guard stays fail-closed, including host OAuth paths and official terminal login. Missing baseline, mismatch, probe failure and same-policy helper restart do not automatically approve an IP or rearm a latched route.
- Strict mode continues to reject unsupported remote/direct/Codex/API-endpoint paths. New service update and migration entry points reuse that policy.
- Subscription encryption, import validation and SSRF restrictions remain intact. Refreshing a subscription cannot establish an approved exit baseline.
- Deployment-level telemetry disable wins over new per-slot controls. Normal request logging, authentication, loopback listeners, key scopes, quota and bounded retry behavior remain.
- HTTP early-close accounting is retained. The new Responses WebSocket adapter now reports completion using the same writable-finished semantics, so its normal and interrupted responses are logged exactly once.
- Existing deployments that need to preserve caller thinking display choices can explicitly set native `compatibility.thinking_display` to `passthrough`. The new upstream `summarized` mode remains available.

## Reviewed failure boundaries

Helper replacement identifies the executable and exact proxy configuration before signaling a process, and serializes stop/start for each proxy. It never treats a matching command-line prefix as ownership.

Docker memory raises compare the requested limit with the live limit as well as saved configuration. Failure handling restores original byte limits, including swap sentinel values, and verifies rollback before reporting success. A failed configuration write must not leave a successful-but-unrecorded raise.

Legacy remote migration treats stop, rename, network disconnection and replacement as a transaction. Failed restoration is reported explicitly instead of being swallowed. Existing network attachments must survive a successful migration.

## Deployment and validation boundaries

This deployment has an intentionally empty fleet. Retired accounts, credentials, independent keys and schedules must not be restored from old backups to test an upgrade. Use isolated Linux tests and empty-instance startup checks; real provider/model acceptance requires a separately authorized, valid account.

Verify source/UI hashes, all pinned payload hashes and compiled helpers against the candidate manifest. Preserve runtime mounts, `.env`, secrets and limits; use a fresh backup of the already-retired state. Never replace live routing configuration with repository defaults. Record any native normalization when saving a configuration field.

A successful IP reflector check does not prove per-destination NAT behavior, and server-side controls do not control an external OAuth browser. These checks do not establish why a provider suspended an account or guarantee future account acceptance.
